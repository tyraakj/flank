# Development Workflow

## Approach

Build this project incrementally using a spec-driven workflow. Read `00-product-map.md` before any other spec. Each numbered spec unit defines one implementation increment — its dependencies, scope limits, and a checklist. Always implement against the spec. Do not infer or invent behavior that is not defined.

## Before Starting Any Unit

Read the following context files in order:

1. `context/project-overview.md` — product definition, goals, agent roster, screens, and scope
2. `context/architecture-context.md` — stack, deployables, system boundaries, storage model, and pipeline invariants
3. `context/ui-context.md` — tokens, components, report state treatments, and layout patterns
4. `context/code-standards.md` — TypeScript, Zod, agent modules, providers, BFF handlers, persistence, and file organization
5. `context/ai-workflow-rules.md` — this file
6. `context/progress-tracker.md` — current phase, completed units, open questions, and next steps

## Scoping Rules

- Work on one spec unit at a time. Each unit has a defined scope and a "Check When Done" list.
- Prefer small, verifiable increments over large speculative changes.
- Do not combine two spec units into a single implementation step unless their dependency list explicitly permits it.
- Do not combine UI changes with worker pipeline changes in the same step.
- Do not implement agent logic and BFF route handlers in the same step.

## When To Split Work

Split an implementation step if it:

- Combines the app deployable and the worker deployable
- Touches both a provider implementation and a stage runner
- Adds a new Prisma model and a report screen in the same change
- Crosses the shared-package boundary without a clear contract first
- Cannot be verified end to end quickly

If a change cannot be verified end to end quickly, the scope is too broad — split it.

## Handling Missing Requirements

- Do not invent product behavior that is not defined in the spec files or context files.
- If a requirement is ambiguous, resolve it in the relevant spec or context file before implementing.
- If a requirement is missing, add it as an open question in `progress-tracker.md` before continuing.

## Protected Components

Do not modify generated third-party foundation components unless explicitly instructed:

- `apps/app/components/ui/*` — shadcn/ui primitives, generated by the CLI
- Third-party library internals

Product behavior, styling, and feature logic live in `apps/app/components/flank/` and `apps/worker/src/`, not inside the foundation components.

## Pipeline Invariants to Enforce

Never violate these during implementation (full list in `architecture-context.md`):

1. The browser never talks to Redis, the worker, or providers directly.
2. BFF handlers enqueue and read — they do not run agents or write stage outputs.
3. Every persisted fact has at least one Evidence row.
4. No stage deletes its predecessors' artifacts on replay.
5. The Critic's retry budget is bounded — no infinite loops.
6. Confidence is computed deterministically from persisted inputs — no live provider calls.

## Keeping Docs In Sync

Update the relevant context file whenever implementation changes:

- Stack or deployable changes → `architecture-context.md`
- New UI conventions or component patterns → `ui-context.md`
- New code conventions or file organization decisions → `code-standards.md`
- Feature scope changes or decisions made → `project-overview.md`
- Any implementation progress → `progress-tracker.md`

Progress state in `progress-tracker.md` must reflect the actual implementation state, not the intended state.

## Before Moving To The Next Unit

1. The current unit's "Check When Done" checklist passes end to end.
2. No pipeline invariant defined in `architecture-context.md` was violated.
3. `progress-tracker.md` reflects the completed unit.
4. App build, worker build, and typecheck pass (`pnpm typecheck`).
5. If the unit touched an agent, provider, or Zod contract — the eval harness still passes (`pnpm evals`) or a baseline update was explicitly justified.
